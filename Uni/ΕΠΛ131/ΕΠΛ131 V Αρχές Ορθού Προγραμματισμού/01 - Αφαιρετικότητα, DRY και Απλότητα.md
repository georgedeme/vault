# 01 - Αφαιρετικότητα, DRY και Απλότητα

Οι αρχές 1–5: η «κορυφαία» αρχή της αφαιρετικότητας και οι αρχές της απλότητας που απορρέουν από αυτή (διαφάνειες V-7 … V-17).

## 1. Αρχή της Αφαιρετικότητας – Abstraction Principle (V-7 … V-9)

> [!note] Ορισμός
> **Κορυφαία** αρχή ορθού προγραμματισμού, η οποία **εμπερικλείει** αρκετές από τις υπόλοιπες, π.χ.
> - Μην επαναλαμβάνεις τον εαυτό σου (DRY)
> - Κράτα το απλό (KISS)
> - Να αποκρύβεις τις λεπτομέρειες
> - Επαναχρησιμοποίηση κώδικα

> [!important] Δύο μορφές, δύο μηχανισμοί
>
> | Μορφή | Αφορά | Μηχανισμός στη Java |
> |---|---|---|
> | **Program abstraction** | τον κώδικα per se | **συνάρτηση/μέθοδος** → αρθρωτές λύσεις (modular solutions), αξιοποίηση βιβλιοθηκών |
> | **Data abstraction** | τα δεδομένα | **αφηρημένοι τύποι δεδομένων / αντικείμενα** → αξιοποίηση κλάσεων αντικειμένων |

### Αναφορές σε αφαιρετικότητα (V-8)

> [!note] Τι σημαίνει στην πράξη
> - Κάθε **σημαντικό τμήμα λειτουργικότητας** πρέπει να υλοποιείται **μόνο μία φορά**.
> - Όπου υπάρχουν **ξεχωριστές, παρόμοιες** συναρτήσεις, να αντικαθίστανται από μια **πιο γενική** συνάρτηση, **με την αφαίρεση των διαφορών** (οι διαφορές γίνονται παράμετροι).
> - Σημαντικό κριτήριο ποιότητας για μια γλώσσα προγραμματισμού είναι **πόσο καλά στηρίζει** την αρχή της αφαιρετικότητας.

### Προσπαθήστε να (V-9)

- Σκέφτεστε **όσο γίνεται πιο αφηρημένα/γενικά**.
- **Γενικεύετε** ένα πρόβλημα για να δείτε τις **αναλογίες** του με άλλα προβλήματα και τις λύσεις τους.
- **Εστιάζετε στην ουσία**, αγνοώντας τη λεπτομέρεια, η οποία μπορεί να εισαχθεί **σταδιακά** στη συνέχεια, όταν και όπου χρειάζεται.

> [!example]- Αφαιρετικότητα στον κώδικα του μαθήματος
> - **`isLeapYear(int year)`** (II-33): η λογική του δίσεκτου κρύβεται πίσω από ένα όνομα· η `main` απλά «ρωτά».
> - **`Math.sqrt`, `Math.random`**: χρησιμοποιούμε βιβλιοθήκες χωρίς να ξέρουμε πώς υλοποιούνται.
> - **Γενίκευση με παράμετρο**: αντί για `printLine5()` και `printLine10()`, μία `printLine(int n)`. Το `displayPrimes(isPrime, n)` (IV-50) δέχεται το «πόσοι ανά γραμμή» ως παράμετρο αντί να έχει «καρφωμένο» το 10.
> - **Data abstraction**: ο πίνακας `String[] deck` αναπαριστά μια «τράπουλα» – σκεφτόμαστε σε επίπεδο «χαρτιά», όχι «bits».

## 2. Μην επαναλαμβάνεις τον εαυτό σου – DRY (V-12)

> [!note] Ορισμός
> **DRY – Don't Repeat Yourself.** Εμπερικλείεται στην αρχή της αφαιρετικότητας: **μόλις αντιληφθείς ότι επαναλαμβάνεις τον εαυτό σου, δημιούργησε μια νέα αφαιρετικότητα**.

> [!important] Άμεσα σχετιζόμενη με…
> …την αλγοριθμική δομή της **επανάληψης** και τις έννοιες της **συνάρτησης/μεθόδου** και της **κλάσης** – επειδή μας επιτρέπουν να **μην** επαναλαμβάνουμε τον εαυτό μας.
>
> Π.χ. έχουμε να ταξινομήσουμε με τον ίδιο τρόπο **δύο ξεχωριστούς πίνακες**. Αντί να γράψουμε τον ίδιο κώδικα δύο φορές, τον ενσωματώνουμε σε μια **συνάρτηση** την οποία καλούμε όσες φορές θέλουμε.

> [!example]- DRY στην πράξη
> **Επανάληψη → βρόχος** (IV-5):
> ```java
> // ✗ WET ("write everything twice")
> a0 = 0.0; a1 = 0.0; a2 = 0.0; … a9 = 0.0;
> // ✓ DRY
> for (int i = 0; i < a.length; i++) a[i] = 0.0;
> ```
> **Επανάληψη → μέθοδος** (IV-26): ο κώδικας ανακατέματος γράφεται **μία** φορά στη `shuffleDeck(String[] deck)` και καλείται για κάθε τράπουλα.
> **Επανάληψη → σταθερά** (IV-24): `int SUITS = suit.length;` αντί να γράφεται το `4` σε πολλά σημεία.

> [!warning] Παγίδα DRY ➕
> Δύο κομμάτια κώδικα που **μοιάζουν** δεν σημαίνει απαραίτητα ότι είναι «το ίδιο πράγμα». Αν αλλάζουν για **διαφορετικούς λόγους**, η συγχώνευσή τους σε μία μέθοδο δημιουργεί σύζευξη (βλ. [[03 - Σχεδιασμός Μονάδων|αρχή της μίας ευθύνης]]). Το DRY αφορά **γνώση/λογική**, όχι απλά κείμενο.

## 3. Κράτα το απλό – KISS (V-13)

> [!note] Ορισμός
> **KISS – Keep It Simple, Stupid!** Κλασική αρχή που **δεν αφορά μόνο τον προγραμματισμό** – τα περισσότερα συστήματα λειτουργούν καλύτερα αν είναι **απλά** παρά περίπλοκα. Κατ' επέκταση η απλότητα πρέπει να συνιστά **βασική αρχή σχεδιασμού**:
> - *Simplicity is best*
> - *Unnecessary complexity should be avoided*

> [!important] Γιατί
> - Ο απλός κώδικας απαιτεί **λιγότερο χρόνο** για να γραφτεί, έχει **λιγότερα σφάλματα** και **διευκολύνει τροποποιήσεις**.
> - **Εξ ορισμού η αφηρημένη σκέψη είναι πιο απλή**, αφού αφαιρεί/κρύβει λεπτομέρεια.
> - **Σύνθετα προβλήματα διασπώνται σε απλούστερα υποπροβλήματα.**

> [!example]- KISS στον κώδικα του μαθήματος
> ```java
> // ✗ πολύπλοκο
> if (year % 4 == 0) {
>     if (year % 100 == 0) {
>         if (year % 400 == 0) isLeapYear = true; else isLeapYear = false;
>     } else isLeapYear = true;
> } else isLeapYear = false;
>
> // ✓ απλό (II-32)
> isLeapYear = (year % 4 == 0) && (year % 100 != 0 || year % 400 == 0);
> ```
> Επίσης: `return s == g;` αντί για `if (s == g) return true; else return false;` (III-72).

## 4. Κάνε το απλούστερο πράγμα που θα μπορούσε να δουλέψει (V-15, V-16)

> [!note] Do the simplest thing that could possibly work
> Μια καλή ερώτηση προς τον εαυτό σας όταν προγραμματίζετε: **«Τι είναι το απλούστερο πράγμα το οποίο θα μπορούσε ενδεχομένως να δουλέψει;»** Σας βάζει στον σωστό δρόμο για απλότητα στον σχεδιασμό.
> - Ενδεχομένως αρχίζετε με κάτι που «δουλεύει» και **σταδιακά** το αντικαθιστάτε με κάτι **απλούστερο** που επίσης «δουλεύει».
> - Η απλότητα σαφώς είναι **κριτήριο «ποιοτικού» σχεδιασμού**.
> - *Σημ.:* **άλλα κριτήρια απόδοσης**, π.χ. ταχύτητα/μνήμη, μπορεί να συνηγορούν προς λύσεις που **δεν** είναι κατ' ανάγκη οι πιο απλές.

> [!tip] Μια καλή τεχνική (V-16)
> Που (έμμεσα) εφαρμόζει την αρχή της απλότητας:
> 1. **Πρώτα** επιλύουμε μια **πιο απλή εκδοχή** του προβλήματος, και
> 2. **Μετά επεκτείνουμε** τη λύση μας για να καλύψει το κανονικό πρόβλημα.
>
> Η επιτυχία/ευκολία της επέκτασης εξαρτάται σε σημαντικό βαθμό από την **καταλληλότητα της άρθρωσης** της λύσης για την απλή εκδοχή – ποιο υπο-πρόβλημα χρειάζεται να επεκταθεί.

> [!example]- Παράδειγμα της τεχνικής: η τράπουλα (IV-15 … IV-27)
> 1. Απλή εκδοχή: τύπωσε **ένα** τυχαίο χαρτί.
> 2. Επέκταση: φτιάξε **όλη** την τράπουλα.
> 3. Επέκταση: **ανακάτεψέ** την.
> 4. Άρθρωση: `createDeck` / `shuffleDeck` / `displayDeck`.
>
> Αντίστοιχα στο `PrintChars` (III-54 … III-58): πρώτα σταθερά όρια `' '`…`'~'`, μετά όρια από τη γραμμή εντολής, μετά χειρισμός ανάποδων ορίων.

## 5. Απέφευγε τη δημιουργία αχρείαστων – YAGNI (V-17)

> [!note] Ορισμός
> **Avoid creating a YAGNI (You Aren't Going to Need It).** Άμεσα συναφής με την αρχή της απλότητας (KISS) και του να επιδιώκεται η πιο απλή λύση που «δουλεύει». Το τι λέει: **μην προσθέτετε λειτουργικότητα πριν τη χρειάζεστε!**
> - Τυχόν **«πλεονασμός» μειώνει την απλότητα** και δυσκολεύει την κατανόηση του κώδικα, δημιουργώντας εύλογα απορίες ως προς τη (λογική της) παρουσία «αχρείαστων» στοιχείων.
> - *Always implement things when you actually need them, never when you just foresee that you need them.*

> [!example]- YAGNI – παραδείγματα
> - Μια `LeapYear` που υποστηρίζει και Ιουλιανό ημερολόγιο «μήπως χρειαστεί».
> - Παράμετροι που δεν χρησιμοποιούνται ποτέ: `static void displayDeck(String[] deck, boolean colored, int columns)` ενώ κανείς δεν τις ζητά.
> - Μεταβλητές που δηλώνονται και δεν χρησιμοποιούνται (ο αναγνώστης αναρωτιέται «γιατί είναι εδώ;»).
> - Το περιττό `for (int i = 0; i < N; i++) cards[i] = 0;` (IV-36) – ο πίνακας έχει ήδη μηδενικά. (Εδώ βέβαια η διαφάνεια IV-7 λέει ότι η ρητή αρχικοποίηση είναι «καλύτερη πρακτική» – οι αρχές μερικές φορές τραβούν σε αντίθετες κατευθύνσεις.)

## Συχνά Λάθη (στις απαντήσεις)

> [!warning] Συχνά Λάθη
> - Σύγχυση **KISS** (απλότητα σχεδιασμού) με **YAGNI** (μη προσθήκη λειτουργικότητας που δεν χρειάζεται): το YAGNI είναι **ειδική περίπτωση** απλότητας.
> - Να λες ότι το DRY αφορά μόνο «copy-paste»: αφορά κάθε επανάληψη γνώσης (σταθερές, τύπους, λογική).
> - Να ξεχνάς τα **δύο είδη** αφαιρετικότητας (program vs data) και τους μηχανισμούς τους.
