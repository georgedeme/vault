# 06 - Ασκήσεις

18 ασκήσεις για την Ενότητα V: ορισμοί, σχέσεις ανάμεσα στις αρχές, και αναγνώριση/διόρθωση παραβιάσεων σε κώδικα. **Λύσε πρώτα, άνοιξε μετά.**

> [!tip] Πώς να απαντάς
> Σε «ποια αρχή παραβιάζεται;» συνήθως υπάρχουν **περισσότερες από μία** σωστές απαντήσεις. Ανέφερε την **κύρια**, εξήγησε **γιατί** με αναφορά στον κώδικα, και πρότεινε **διόρθωση**.

---

## Μέρος Α — Ορισμοί και σχέσεις

### Άσκηση 1

Ποια αρχή χαρακτηρίζεται ως «κορυφαία» και ποιες άλλες αρχές εμπερικλείει; Ποια είναι τα δύο είδη της και οι μηχανισμοί τους στη Java;

> [!success]- Λύση
> Η **Αρχή της Αφαιρετικότητας** (Abstraction Principle). Εμπερικλείει: **DRY**, **KISS**, **απόκρυψη λεπτομερειών**, **επαναχρησιμοποίηση κώδικα**.
> - **Program abstraction** → συναρτήσεις/μέθοδοι (αρθρωτές λύσεις, βιβλιοθήκες)
> - **Data abstraction** → αφηρημένοι τύποι δεδομένων / αντικείμενα (κλάσεις)

### Άσκηση 2

Εξήγησε τη διαφορά σύζευξης και συνοχής. Ποιον συνδυασμό επιδιώκουμε και γιατί;

> [!success]- Λύση
> **Σύζευξη**: βαθμός αλληλεξάρτησης **ανάμεσα** σε μονάδες. **Συνοχή**: βαθμός συνάφειας των στοιχείων **μέσα** σε μια μονάδα.
> Επιδιώκουμε **χαλαρή σύζευξη + ισχυρή συνοχή** → αναγνωσιμότητα και συντηρησιμότητα· κάθε μονάδα είναι αυτοδύναμη (δοκιμάζεται/επαναχρησιμοποιείται ανεξάρτητα) και έχει σαφή σκοπό.

### Άσκηση 3

«Μια μονάδα με ένα μόνο στοιχείο έχει τέλεια συνοχή, άρα είναι ο ιδανικός σχεδιασμός.» Σωστό ή λάθος;

> [!success]- Λύση
> **Λάθος** (V-31). Θεωρητικά έχει «τέλεια» συνοχή, αλλά στην πράξη χρειάζεται **ισοζύγιο** ανάμεσα σε συνοχή, πολυπλοκότητα ατομικών στοιχείων και σύζευξη: τα μοναδιαία στοιχεία είναι είτε **πολύ περίπλοκα** είτε **πολύ περιορισμένα και ισχυρά συζευγμένα** με άλλα.

### Άσκηση 4

Πώς σχετίζεται ο Νόμος της Δήμητρας με (α) τη χαλαρή σύζευξη (β) την απόκρυψη πληροφοριών (γ) την πολυ-επίπεδη αρχιτεκτονική;

> [!success]- Λύση
> (α) Είναι **ειδική περίπτωση** χαλαρής σύζευξης – κάθε μονάδα γνωρίζει λίγα για τις άλλες.
> (β) **Σχετίζεται** άμεσα: η απόκρυψη λέει «μη δείχνεις τα εσωτερικά σου», ο LoD «μην ψάχνεις τα εσωτερικά των άλλων».
> (γ) Η πολυ-επίπεδη αρχιτεκτονική είναι **ένας τρόπος υλοποίησής** του: οι κλήσεις περιορίζονται στο ίδιο ή στο αμέσως κατώτερο στρώμα.

### Άσκηση 5

Εξήγησε το «premature optimization is the root of all evil». Γιατί η διαφάνεια προτιμά τον όρο «ποιοτική βελτίωση»;

> [!success]- Λύση
> (Knuth) Δεν βελτιστοποιούμε πριν έχουμε **ορθό** πρόγραμμα· η «βελτιστοποίηση» δεν οδηγεί κατ' ανάγκη σε «βέλτιστο», και το «βέλτιστο» θέλει **κριτήρια** (ταχύτητα; μνήμη;).
> «Ποιοτική βελτίωση»: βάσει των αρχών, με ιεραρχία – τα **υψηλά** επίπεδα (σχεδιασμός) έχουν τη μεγαλύτερη επίδραση και είναι δύσκολο να αλλάξουν αργότερα· οι βελτιώσεις ταχύτητας/μνήμης είναι συνήθως **τοπικές** αλλαγές στα **χαμηλά** επίπεδα, απλές αλλά με καθολική επίδραση.

### Άσκηση 6

Είναι αντιφατικές οι αρχές YAGNI και Embrace Change;

> [!success]- Λύση
> **Όχι.** Το YAGNI απαγορεύει να γράφεις **σήμερα** κώδικα για αλλαγές που **ίσως** χρειαστούν. Το Embrace Change ζητά ο κώδικας να είναι **δομημένος** ώστε, **όταν** έρθει η αλλαγή, να γίνει με ελεγχόμενο, προβλέψιμο τρόπο. Το ένα αφορά **ποσότητα** κώδικα, το άλλο **ποιότητα δομής**.

### Άσκηση 7

Γιατί «οι συναρτήσεις `main` δεν επαναχρησιμοποιούνται»; Τι συνέπεια έχει αυτό για τον τρόπο που γράφουμε προγράμματα;

> [!success]- Λύση
> Η `main` είναι το σημείο εισόδου **ενός συγκεκριμένου** προγράμματος (διαβάζει `args`, τυπώνει) – άλλο πρόγραμμα δεν μπορεί να την «καλέσει» χρήσιμα. Άρα **η χρήσιμη λογική πρέπει να βγαίνει σε μεθόδους** (π.χ. `isLeapYear`, `shuffleDeck`), που μπορούν να επαναχρησιμοποιηθούν. Άρθρωση → επαναχρησιμοποίηση (V-43).

## Μέρος Β — Βρες την αρχή που παραβιάζεται

### Άσκηση 8

```java
double avg1 = (g1[0] + g1[1] + g1[2] + g1[3] + g1[4]) / 5.0;
double avg2 = (g2[0] + g2[1] + g2[2] + g2[3] + g2[4]) / 5.0;
double avg3 = (g3[0] + g3[1] + g3[2] + g3[3] + g3[4]) / 5.0;
```

> [!success]- Λύση
> **DRY** (και Αφαιρετικότητα): ο ίδιος υπολογισμός τρεις φορές, με «καρφωμένο» μέγεθος 5. Διόρθωση:
> ```java
> static double average(double[] a) {
>     double sum = 0.0;
>     for (double v : a) sum += v;
>     return sum / a.length;
> }
> double avg1 = average(g1), avg2 = average(g2), avg3 = average(g3);
> ```
> Επίσης βοηθά **Embrace change**: αν οι βαθμοί γίνουν 6, δεν αλλάζει τίποτα.

### Άσκηση 9

```java
static int count;       // καθολική
static void countEvens(int[] a) { for (int v : a) if (v % 2 == 0) count++; }
static void countPositives(int[] a) { for (int v : a) if (v > 0) count++; }
```

> [!success]- Λύση
> **Minimize Coupling**: οι δύο μέθοδοι μοιράζονται την καθολική `count` – το αποτέλεσμα της μίας εξαρτάται από το αν κλήθηκε πρώτα η άλλη (και αν κάποιος θυμήθηκε να μηδενίσει). Επίσης **Least astonishment**.
> Διόρθωση: τοπική μεταβλητή και `return`:
> ```java
> static int countEvens(int[] a) {
>     int count = 0;
>     for (int v : a) if (v % 2 == 0) count++;
>     return count;
> }
> ```

### Άσκηση 10

```java
// Επιστρέφει το μέγιστο στοιχείο του πίνακα
static int max(int[] a) {
    java.util.Arrays.sort(a);
    return a[a.length - 1];
}
```

> [!success]- Λύση
> **Least astonishment**: το όνομα και το σχόλιο λένε «επιστρέφει το μέγιστο», αλλά η μέθοδος **ταξινομεί τον πίνακα του καλούντα** (οι πίνακες περνούν ως αναφορές) – κρυφή παρενέργεια. Επίσης **Single Responsibility** (κάνει δύο πράγματα). Διόρθωση: απλή σάρωση με `max = a[0]` ([[02 - Βασική Επεξεργασία Πινάκων|IV – 02]]).

### Άσκηση 11

```java
public static void main(String[] args) {
    // 80 γραμμές: διάβασμα args, δημιουργία πίνακα, ανακάτεμα,
    // υπολογισμός στατιστικών, εκτύπωση σε μορφή πίνακα
}
```

> [!success]- Λύση
> **Single Responsibility** και **Separation of Concerns**: μία μέθοδος με πολλές ευθύνες και πολλούς λόγους αλλαγής. Επίσης **Don't make me think** (δύσκολη ανάγνωση) και δεν επιτρέπει **επαναχρησιμοποίηση** (η `main` δεν επαναχρησιμοποιείται).
> Διόρθωση: `createX` / `processX` / `displayX` όπως στην τράπουλα (IV-27).

### Άσκηση 12

```java
if (n % 2 == 0) isEven = true; else isEven = false;
if (isEven == true) System.out.println("even");
```

> [!success]- Λύση
> **KISS** / **Don't make me think**: περιττή πολυπλοκότητα. `isEven = n % 2 == 0;` και `if (isEven)`.

### Άσκηση 13

```java
static void displayDeck(String[] deck, boolean colored, int columns, String separator,
                        boolean reverse, boolean shuffleFirst) { … }
// όλες οι κλήσεις στο πρόγραμμα: displayDeck(deck, false, 1, "\n", false, false);
```

> [!success]- Λύση
> **YAGNI**: πέντε παράμετροι για λειτουργικότητα που κανείς δεν χρησιμοποιεί («μήπως χρειαστεί»). Επίσης το `shuffleFirst` παραβιάζει **Single Responsibility** και **Least astonishment** (μια `display` που ανακατεύει). Διόρθωση: `displayDeck(String[] deck)`.

### Άσκηση 14

```java
for (int i = 0; i < 52; i++) { … }
int r = i + (int) (Math.random() * (52 - i));
String[] deck = new String[52];
```

> [!success]- Λύση
> «Hardwired» σταθερές (IV-24): παραβιάζει **DRY** (η ίδια γνώση – «η τράπουλα έχει 52 χαρτιά» – σε πολλά σημεία) και **Embrace change** (τράπουλα 32 φύλλων → αλλαγή σε πολλά σημεία, με κίνδυνο να ξεχαστεί κάποιο). Διόρθωση: `N = SUITS * RANKS` και `deck.length`.

### Άσκηση 15

```java
int a = x; x = y; y = a;              // εκδοχή Α
x = x ^ y; y = x ^ y; x = x ^ y;      // εκδοχή Β – «πιο γρήγορη, χωρίς επιπλέον μεταβλητή»
```

> [!success]- Λύση
> Η Β παραβιάζει **Avoid premature optimization** (αμελητέο κέρδος) και **Don't make me think** / **Code for the maintainer** (δυσνόητη). (Μάλιστα, αν `x` και `y` είναι το **ίδιο** στοιχείο πίνακα, π.χ. `a[i] ^= a[j]` με `i == j`, το μηδενίζει.) Προτιμάται η Α.

## Μέρος Γ — Σχεδίασε

### Άσκηση 16

Ξαναγράψε το `PrimeSieve` (IV-49) σε αρθρωτή μορφή. Ποιες μέθοδοι και ποιες αρχές εφαρμόζεις;

> [!success]- Λύση
> ```java
> public class PrimeSieve {
>     public static boolean[] sieve(int N) {                 // Δημιουργία/Επεξεργασία
>         boolean[] isPrime = new boolean[N+1];
>         for (int i = 2; i <= N; i++) isPrime[i] = true;
>         for (int i = 2; i*i <= N; i++)
>             if (isPrime[i])
>                 for (int j = i; i*j <= N; j++) isPrime[i*j] = false;
>         return isPrime;
>     }
>
>     public static int countPrimes(boolean[] isPrime) {     // Υπολογισμός
>         int primes = 0;
>         for (int i = 2; i < isPrime.length; i++)
>             if (isPrime[i]) primes++;
>         return primes;
>     }
>
>     public static void displayPrimes(boolean[] isPrime, int n) { … }   // Παρουσίαση (IV-50)
>
>     public static void main(String[] args) {
>         int N = Integer.parseInt(args[0]);
>         boolean[] isPrime = sieve(N);
>         System.out.println("The number of primes <= " + N + " is " + countPrimes(isPrime));
>         displayPrimes(isPrime, 10);
>     }
> }
> ```
> Αρχές: **Single Responsibility**, **Separation of Concerns**, **Code reuse** (`sieve` χρησιμοποιείται και από άλλα προγράμματα), **Hide implementation** (ο καλών δεν ξέρει ότι χρησιμοποιείται κόσκινο), **Open/Closed** (νέες λειτουργίες = νέες μέθοδοι).

### Άσκηση 17

Στο `CouponCollector` της IV-36 οι μέθοδοι `allCollected` και `sum` είναι `private`. Ποια αρχή εφαρμόζεται; Θα άλλαζες κάτι;

> [!success]- Λύση
> **Hide Implementation Details**: είναι καθαρά **βοηθητικές**, άρα δεν χρειάζεται να είναι γνωστές έξω από την κλάση. Επίσης **Single Responsibility** (κάθε μία κάνει ένα πράγμα).
> Βελτιώσεις: (α) η `sum` είναι γενικής χρήσης – θα μπορούσε να μπει σε βοηθητική κλάση/βιβλιοθήκη (**Code reuse**, **Cohesion**)· (β) το περιττό `cards[i] = 0` (**YAGNI**)· (γ) η `allCollected` σαρώνει τον πίνακα σε κάθε επανάληψη – η εκδοχή IV-34 με μετρητή είναι πιο γρήγορη, αλλά αυτή είναι **ποιοτική βελτίωση** που γίνεται **τοπικά** αν χρειαστεί (όχι πρόωρα).

### Άσκηση 18

Εφάρμοσε την τεχνική «πρώτα απλή εκδοχή, μετά επέκταση» (V-16) για το πρόγραμμα: «διάβασε Ν βαθμούς από τον χρήστη (έγκυροι 0–10), τύπωσε μέσο όρο, μέγιστο και πόσοι πέρασαν (≥ 5)».

> [!success]- Λύση
> 1. **Απλή εκδοχή:** διάβασε Ν αριθμούς (χωρίς έλεγχο) σε πίνακα και τύπωσέ τους.
> 2. **Επέκταση 1:** `average(double[] a)`.
> 3. **Επέκταση 2:** `max(double[] a)`, `countAtLeast(double[] a, double limit)` – η παράμετρος `limit` αντί για «καρφωμένο» 5 (**Αφαιρετικότητα**: γενίκευση με αφαίρεση διαφορών).
> 4. **Επέκταση 3:** έλεγχος εγκυρότητας με `do-while` σε μέθοδο `readGrade(Scanner in)`.
>
> Κάθε βήμα δοκιμάζεται πριν το επόμενο· η **άρθρωση** του βήματος 1 (ξεχωριστή μέθοδος ανάγνωσης) κάνει το βήμα 4 τοπική αλλαγή (**Embrace change**).
