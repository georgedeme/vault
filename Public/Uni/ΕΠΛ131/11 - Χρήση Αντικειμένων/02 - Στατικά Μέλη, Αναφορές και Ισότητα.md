# 02 - Στατικά Μέλη, Αναφορές και Ισότητα

Οι τρεις βασικές σημασιολογικές διακρίσεις σε επίπεδο κλάσης (`public`/`private`, `static`/non-`static`, πεδίο/μέθοδος), πώς συμπεριφέρονται οι **αναφορές** αντικειμένων στη μνήμη, τι είναι το **aliasing**, και η κρίσιμη διαφορά ανάμεσα στον τελεστή **`==`** και τη μέθοδο **`equals()`** (διαφάνειες XI-21 … XI-27).

## 1. Οι 3 Σημασιολογικές Διακρίσεις — Οι 8 Συνδυασμοί (XI-21 … XI-23)

Σε επίπεδο μιας κλάσης `C`, κάθε μέλος χαρακτηρίζεται από τρεις ανεξάρτητους άξονες (XI-21):
1. **Ορατότητα**: `public` έναντι `private`
2. **Επίπεδο**: `static` (κλάσης / *class*) έναντι μη-`static` (αντικειμένου / *instance*)
3. **Είδος**: πεδίο/μεταβλητή (*field/variable*) έναντι μεθόδου (*method*)

Αυτό δίνει $2 \times 2 \times 2 = 8$ δυνατούς συνδυασμούς (XI-22, XI-23):

| Συνδυασμός | Ονομασία | Πρόσβαση έξω από τη `C` | Σχόλιο / Ορθή χρήση |
|---|---|---|---|
| `public static` μέθοδος `m` | class method | Ναι, ως **`C.m(…)`** | Ανήκει στο API της `C` (π.χ. `Math.sqrt`, `Luminance.lum`) |
| `public static` μεταβλητή `v` | class variable | Ναι, ως **`C.v`** | Δημόσια καθολική μεταβλητή, ανήκει στο API (π.χ. `Math.PI`, `Color.RED`) |
| `private static` μέθοδος `m` | class method | Όχι | Βοηθητική στατική μέθοδος ιδιωτικής χρήσης |
| `private static` μεταβλητή `v` | class variable | Όχι | Καθολική μεταβλητή ιδιωτικής χρήσης (π.χ. πίνακας `memo` στην Ενότητα X) |
| `public` μη-στατική μέθοδος `m` | **instance method** (μέθοδος αναφοράς) | Ναι, **μόνο μέσω αντικειμένου**: **`obj.m(…)`** | Το API των αντικειμένων της `C` (π.χ. `mydeck.shuffle()`) |
| `public` μη-στατική μεταβλητή `v` | instance variable | Ναι, μόνο μέσω αντικειμένου: `obj.v` | <span class="hl-red">Καλύτερα να αποφεύγονται!</span> (παραβιάζουν την ενθυλάκωση) |
| `private` μη-στατική μέθοδος `m` | instance method | Όχι | Βοηθητική μέθοδος αναφοράς ιδιωτικής χρήσης (lean interfaces) |
| `private` μη-στατική μεταβλητή `v` | **instance variable** (πεδίο αντικειμένου) | Όχι | <span class="hl-green">Η ορθή χρήση</span> για την εσωτερική κατάσταση αντικειμένων |

> [!important] Πώς ξεχωρίζεις αμέσως μια κλήση στον κώδικα
> - **`ΌνομαΚλάσης.μέθοδος(…)`** (π.χ. `Luminance.toGray(c)`, `StdDraw.setPenColor(c)`) → **στατική μέθοδος** (`static`).
> - **`μεταβλητήΑντικειμένου.μέθοδος(…)`** (π.χ. `pic.width()`, `mydeck.shuffle()`, `c.getRed()`) → **μέθοδος αναφοράς** (μη-`static`).

## 2. Κλάσεις χωρίς Instance Members (XI-24)

> [!note] Η παρατήρηση της διαφάνειας XI-24
> Μια κλάση που δεν έχει καθόλου *instance variables* ή *instance methods* (δηλαδή περιέχει μόνο `static` μέλη, όπως οι βιβλιοθήκες `Math`, `StdDraw`, `Luminance`) **δεν δημιουργεί ξεχωριστά αντικείμενα**, διότι τυχόν περιπτώσεις της θα ήταν απόλυτα ταυτόσημες μεταξύ τους (δεν μπορούν να διαφοροποιηθούν).

> [!warning] ⚠️ Σημείωση (XI-24) — Εννοιολογικό vs συντακτικό στη Java
> Η παρατήρηση ισχύει **εννοιολογικά** (σχεδιασμός ΑΤΔ): δεν έχει κανένα νόημα να φτιάξεις `new Luminance()`. Συντακτικά όμως, η Java προσθέτει αυτόματα έναν default `public` κατασκευαστή αν δεν γράψεις κανέναν — άρα `new Luminance()` θα μεταγλωττιζόταν! Για να το απαγορεύσει ρητά μια βιβλιοθήκη (όπως η `java.lang.Math`), ορίζει έναν `private` κατασκευαστή (`private Math() {}`).

## 3. Αναφορές (Διευθύνσεις) και Aliasing (XI-25, XI-26)

> [!important] Χρυσός κανόνας (XI-25)
> **Οι ονομασίες περιπτώσεων αντικειμένων είναι διευθύνσεις**, ακριβώς όπως συμβαίνει και με τους πίνακες.

Δες το παράδειγμα της διαφάνειας XI-26:

```java
DeckObj deck1 = new DeckObj();
DeckObj deck2 = new DeckObj();
DeckObj deck3 = deck1;
```

- `deck1` και `deck2` δημιουργήθηκαν με δύο ξεχωριστά `new`: είναι **δύο διαφορετικά αντικείμενα** σε διαφορετικές διευθύνσεις στη μνήμη, έστω κι αν αρχικά έχουν τα ίδια φύλλα με την ίδια σειρά.
  - Άρα **`deck1 == deck2`** είναι **`false`** (**ΟΧΙ!**).
- `deck3 = deck1` **δεν** αντιγράφει την τράπουλα! Αντιγράφει μόνο τη **διεύθυνση** (αναφορά). Τώρα `deck1` και `deck3` δείχνουν στο **ίδιο αντικείμενο** (<span class="hl-blue">aliasing</span>).
  - Άρα **`deck1 == deck3`** είναι **`true`** (**ΝΑΙ!**).

## 4. Copy Constructor και `==` έναντι `equals()` (XI-27)

Η αρχική `DeckObj` (XI-14) δεν είχε μέθοδο σύγκρισης περιεχομένου, αλλά μπορεί εύκολα να επεκταθεί χωρίς να επηρεαστούν οι υπόλοιπες μέθοδοί της:

| Νέα μέθοδος στο API της `DeckObj` | Ρόλος |
|---|---|
| `DeckObj(DeckObj d)` | **Copy constructor** — κατασκευάζει ένα **νέο** αντικείμενο `DeckObj` με το ίδιο περιεχόμενο (κατάσταση) όπως το `d`. |
| `boolean equals(DeckObj d)` | Συγκρίνει το **περιεχόμενο** (αν τα φύλλα των δύο τραπουλών είναι στην ίδια σειρά), όχι τις διευθύνσεις. |

Ας ιχνηλατήσουμε βήμα-βήμα το παράδειγμα της XI-27:

```java
DeckObj deck1 = new DeckObj();
DeckObj deck2 = new DeckObj(deck1); // Νέο αντικείμενο (αντίγραφο): deck2 == deck1 → false, deck2.equals(deck1) → true
DeckObj deck3 = deck1;              // Alias (ίδια διεύθυνση):       deck3 == deck1 → true,  deck3.equals(deck1) → true
deck3.shuffle();                    // Αλλάζει το κοινό αντικείμενο των deck1 & deck3!
                                    // deck3 == deck1 → true  &&  deck1.equals(deck3) → true
                                    // deck2.equals(deck1) → false! (η deck2 έμεινε ανέπαφη)
```

> [!important] Οι δύο γενικοί κανόνες για `==` και `equals()` (XI-27)
> 1. **Εάν `Obj1 == Obj2` τότε `Obj1.equals(Obj2)`** *(το ίδιο αντικείμενο είναι πάντα ίσο με τον εαυτό του)*.
> 2. **Εάν `!Obj1.equals(Obj2)` τότε `Obj1 != Obj2`** *(αν έχουν διαφορετικό περιεχόμενο, αποκλείεται να είναι το ίδιο αντικείμενο — το αντιθετοαντίστροφο του 1)*.
>
> **Προσοχή:** Τα αντίστροφα **ΔΕΝ** ισχύουν!
> - `Obj1.equals(Obj2)` μπορεί να είναι `true` ενώ `Obj1 != Obj2` (δύο ξεχωριστά αντικείμενα με ίδιο περιεχόμενο, π.χ. `deck1` και `deck2` πριν το `shuffle()`, ή δύο `new Color(255, 0, 0)`).
> - `Obj1 != Obj2` δεν συνεπάγεται `!Obj1.equals(Obj2)`.

> [!warning] ⚠️ Σημείωση & ➕ Παγίδες εξετάσεων με `==`, `equals()` και `null`
> 1. **Παγίδα `null` στον Κανόνα 1 (XI-27)**: Αν `Obj1 == null` και `Obj2 == null`, τότε `Obj1 == Obj2` είναι `true`, αλλά η κλήση `Obj1.equals(Obj2)` πετά **`NullPointerException`**! Ο κανόνας 1 ισχύει εφόσον `Obj1 != null`. (Αντίστροφα, αν `Obj1 != null` και `Obj2 == null`, μια σωστά υλοποιημένη `Obj1.equals(null)` επιστρέφει `false`.)
> 2. **Παγίδα προεπιλεγμένης `equals()`**: Κάθε κλάση στη Java κληρονομεί μια προεπιλεγμένη `equals()` από την `Object` η οποία **συγκρίνει διευθύνσεις (όπως το `==`)** αν η κλάση δεν γράψει τη δική της `equals()`! Γι' αυτό `String`, `Color` κ.ά. υλοποιούν τη δική τους `equals()`.
> 3. **Παγίδα `String` με `==`**: Με `String` μην χρησιμοποιείς **ποτέ** `==` για σύγκριση κειμένου — πάντα `s1.equals(s2)` (δύο `new String("hi")` έχουν `s1 == s2` → `false`, `s1.equals(s2)` → `true`).

## Συχνά Λάθη

- **Χρήση `==` αντί για `.equals()`** για έλεγχο ισότητας περιεχομένου σε `String`, `Color`, `DeckObj` κ.λπ.
- **Να νομίζεις ότι `DeckObj d3 = d1;` φτιάχνει αντίγραφο**: φτιάχνει **alias**· για ανεξάρτητο αντίγραφο χρειάζεται copy constructor (`new DeckObj(d1)`).
- **Κλήση μη-στατικής μεθόδου από το όνομα της κλάσης**: `DeckObj.shuffle()` είναι σφάλμα μεταγλώττισης — οι μέθοδοι αναφοράς καλούνται **πάντα** σε αντικείμενο (`mydeck.shuffle()`).
- **Δήλωση πεδίων ως `public`**: παραβιάζει την ενθυλάκωση· τα instance variables πρέπει να είναι `private` (XI-23).
