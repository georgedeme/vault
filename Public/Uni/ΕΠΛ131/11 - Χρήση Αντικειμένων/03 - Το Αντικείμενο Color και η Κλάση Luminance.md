# 03 - Το Αντικείμενο Color και η Κλάση Luminance

Ο αφηρημένος τύπος **`java.awt.Color`**, η έννοια της **αμεταβλητότητας (immutability)**, η βιβλιοθήκη στατικών μεθόδων **`Luminance`**, τα παραδείγματα **`AlbersSquares` / `AlbersS`**, η παγίδα **εμβέλειας** στο `do-while`, ο **garbage collector** στην πράξη, και η αναπαράσταση αντικειμένων στη μνήμη (διαφάνειες XI-28 … XI-51).

## 1. Το Αντικείμενο `java.awt.Color` (XI-28 … XI-32)

Η `Color` είναι έτοιμη κλάση της Java στο πακέτο **`java.awt`** — για να τη χρησιμοποιήσουμε γράφουμε στην κορυφή του αρχείου:

```java
import java.awt.Color;
```

- **Χρώμα**: η αίσθηση του ματιού από την ηλεκτρομαγνητική ακτινοβολία (XI-31).
- **Σύνολο τιμών (RGB αναπαράσταση)**: $256^3 = 16.777.216$ δυνατές τιμές (**24 bits**), όπου οι συνιστώσες κόκκινου (**R**), πράσινου (**G**) και μπλε (**B**) παίρνουν ακέραιες τιμές από **`0` έως `255`** (XI-31).

| R | G | B | Χρώμα |
|---:|---:|---:|---|
| 255 | 0 | 0 | Κόκκινο |
| 0 | 255 | 0 | Πράσινο |
| 0 | 0 | 255 | Μπλε |
| 255 | 255 | 255 | Άσπρο |
| 0 | 0 | 0 | Μαύρο |
| 255 | 0 | 255 | Magenta (φούξια) |
| 105 | 105 | 105 | Γκρι (όταν $R = G = B$) |

### API της `java.awt.Color` (XI-29, XI-32)

| Μέθοδος | Κατηγορία | Περιγραφή |
|---|---|---|
| `Color(int r, int g, int b)` | Κατασκευαστής | Δημιουργεί χρώμα με συνιστώσες `r, g, b ∈ [0, 255]` |
| `int getRed()` | Ανακτητής | Επιστρέφει την ένταση του κόκκινου (`0..255`) |
| `int getGreen()` | Ανακτητής | Επιστρέφει την ένταση του πράσινου (`0..255`) |
| `int getBlue()` | Ανακτητής | Επιστρέφει την ένταση του μπλε (`0..255`) |
| `Color brighter()` | Ανακτητής / εργοστασιακή | Επιστρέφει **νέο** `Color`, πιο φωτεινή εκδοχή αυτού του χρώματος |
| `Color darker()` | Ανακτητής / εργοστασιακή | Επιστρέφει **νέο** `Color`, πιο σκοτεινή εκδοχή αυτού του χρώματος |
| `String toString()` | Ανακτητής | Συμβολοσειρά αναπαράστασης του χρώματος |
| `boolean equals(Object o)` | Ανακτητής | Ελέγχει αν δύο χρώματα έχουν τις ίδιες RGB τιμές (XI-29) |

> [!warning] ➕ Παγίδα ορίων στον κατασκευαστή `Color(r, g, b)`
> Αν περάσεις τιμή εκτός `[0, 255]` (π.χ. `-1` ή `256`), ο κατασκευαστής πετά **`IllegalArgumentException`** στον χρόνο εκτέλεσης. Γι' αυτό για τυχαίο χρώμα γράφουμε `(int)(Math.random() * 256)` (δίνει `0..255`), ποτέ `* 257`.

## 2. Αμεταβλητότητα (Immutability) της `Color` (XI-33)

> [!important] Γιατί η `Color` είναι αμετάβλητη (XI-33)
> - Το αντικείμενο `Color` **δεν περιλαμβάνει καμία μέθοδο μεταλλάκτη**.
> - Από τη στιγμή που κατασκευαστεί μια περίπτωση `Color`, η εσωτερική κατάστασή της **δεν μπορεί να τροποποιηθεί** — το χρώμα μπορεί μόνο να **ξανα-κατασκευαστεί**.
> - **Ασφαλιστική δικλίδα**: όταν υπάρχουν πολλαπλές αναφορές στο ίδιο `Color` (π.χ. πολλά pixels στο upscaling/downscaling εικόνων), καμία δεν μπορεί να αλλοιώσει απρόσμενα το χρώμα των άλλων!

```java
Color c1 = new Color(255, 0, 0), c2 = c1;  // c1 και c2 δείχνουν στο ΙΔΙΟ αντικείμενο
c2 = c2.darker();                           // Φτιάχνει ΝΕΟ αντικείμενο Color· η c1 μένει (255,0,0)!
```

> [!warning] ➕ Κλασική παγίδα: `c2.darker();` χωρίς ανάθεση!
> Επειδή η `darker()` **δεν** τροποποιεί το `c2` αλλά επιστρέφει ένα **νέο** `Color`, η σκέτη εντολή:
> ```java
> c2.darker(); // ❌ ΔΕΝ αλλάζει το c2! Το νέο αντικείμενο πετιέται!
> ```
> δεν έχει **κανένα** αποτέλεσμα στη `c2` (ακριβώς όπως και η `s.toUpperCase();` στη `String`). Πρέπει πάντα να γράφουμε **`c2 = c2.darker();`**.

## 3. `AlbersSquares` και `Albers` (XI-34 … XI-36)

Το πρόγραμμα `AlbersSquares` διαβάζει δύο RGB χρώματα από τη γραμμή εντολής (`java AlbersSquares 9 90 166 100 100 100`) και σχεδιάζει δύο ζεύγη ομόκεντρων τετραγώνων (το ίδιο χρώμα δείχνει διαφορετικό ανάλογα με το φόντο του — οπτική ψευδαίσθηση του Josef Albers). Χρησιμοποιεί `StdDraw.setPenColor(Color c)` και `StdDraw.filledSquare(double x, double y, double r)` (όπου `r` είναι η **μισή** πλευρά).

```java
import java.awt.Color;

public class AlbersSquares {
   public static void main(String[] args) {
      int r1 = Integer.parseInt(args[0]);
      int g1 = Integer.parseInt(args[1]);
      int b1 = Integer.parseInt(args[2]);
      Color c1 = new Color(r1, g1, b1);

      int r2 = Integer.parseInt(args[3]);
      int g2 = Integer.parseInt(args[4]);
      int b2 = Integer.parseInt(args[5]);
      Color c2 = new Color(r2, g2, b2);

      StdDraw.setPenColor(c1);
      StdDraw.filledSquare(.25, .5, .2);
      StdDraw.setPenColor(c2);
      StdDraw.filledSquare(.25, .5, .1);

      StdDraw.setPenColor(c2);
      StdDraw.filledSquare(.75, .5, .2);
      StdDraw.setPenColor(c1);
      StdDraw.filledSquare(.75, .5, .1);
   }
}
```

Στην παραλλαγή **`Albers`** (XI-36), αντί για `args[]`, τα δύο χρώματα επιλέγονται τυχαία με `(int)(Math.random() * 256)` για κάθε συνιστώσα.

## 4. Η Βιβλιοθήκη `Luminance` (XI-37 … XI-39, XI-49, XI-50)

Η `Luminance` είναι μια **βιβλιοθήκη στατικών μεθόδων** (χωρίς instance variables/methods) που δέχεται και/ή επιστρέφει αντικείμενα `Color`:

- **Φωτεινότητα (NTSC φόρμουλα, XI-37)**:
  $$Y = 0.299\,r + 0.587\,g + 0.114\,b$$
  *(Παρατηρήστε ότι $0.299 + 0.587 + 0.114 = 1.000$, άρα για $r, g, b \in [0, 255]$ ισχύει $Y \in [0.0, 255.0]$. Το ανθρώπινο μάτι είναι πιο ευαίσθητο στο πράσινο και λιγότερο στο μπλε.)*
- **Συμβατότητα χρωμάτων (XI-38)**: δύο χρώματα είναι ευανάγνωστα μαζί (π.χ. γραμματοσειρά και φόντο) όταν η απόλυτη διαφορά φωτεινότητας είναι **$\ge 128.0$**.
- **Μετατροπή σε απόχρωση του γκρι (XI-49)**: όταν $R = G = B = y$, το χρώμα είναι απόχρωση του γκρι (`0` μαύρο … `255` άσπρο). Υπολογίζουμε `y = (int) Math.round(lum(c))` και επιστρέφουμε `new Color(y, y, y)`.

```java
import java.awt.Color;

public class Luminance {
   public static double lum(Color c) {
      int r = c.getRed();
      int g = c.getGreen();
      int b = c.getBlue();
      return .299*r + .587*g + .114*b;
   }

   public static boolean compatible(Color a, Color b) {
      return Math.abs(lum(a) - lum(b)) >= 128.0;
   }

   public static Color toGray(Color c) {
      int y = (int) Math.round(lum(c));
      Color gray = new Color(y, y, y);
      return gray;
   }
}
```

> [!example]- Παράδειγμα `toGray` (XI-49)
> Για το μπλε `Color(9, 90, 166)`:
> $$Y = 0.299 \cdot 9 + 0.587 \cdot 90 + 0.114 \cdot 166 = 2.691 + 52.830 + 18.924 = 74.445$$
> `Math.round(74.445)` → `74L` (`long`) → `(int)` → `74` → `new Color(74, 74, 74)`.
> *(Προσοχή: η `Math.round(double)` επιστρέφει **`long`**, γι' αυτό είναι υποχρεωτικό το cast `(int)` πριν το περάσουμε στον `new Color(y, y, y)`!)*

> [!warning] ⚠️ Σημείωση (XI-38)
> Στο οπτικό παράδειγμα διαφορών φωτεινότητας της διαφάνειας XI-38, το πρώτο πλαίσιο αναγράφει `256`. Επειδή $0 \le Y \le 255$, η μέγιστη δυνατή διαφορά $|Y(a) - Y(b)|$ (άσπρο έναντι μαύρου) είναι **`255.0`**, όχι `256`.

## 5. Παγίδα Εμβέλειας (Scope) στο `do-while` (XI-40 … XI-43)

Θέλουμε η `Albers` να παράγει τυχαία χρώματα **μέχρι να βρει δύο συμβατά**. Αν γράψουμε (XI-40):

```java
do {
   int r1 = (int)(Math.random()*256); // ...
   Color c1 = new Color(r1, g1, b1);  // ❌ δηλωμένη ΜΕΣΑ στο block του do!
   // ...
   Color c2 = new Color(r2, g2, b2);  // ❌ δηλωμένη ΜΕΣΑ στο block του do!
} while (!Luminance.compatible(c1, c2)); // ❌ error: cannot find symbol c1, c2
StdDraw.setPenColor(c1);                 // ❌ error: cannot find symbol c1
```

Ο μεταγλωττιστής βγάζει **6 σφάλματα `cannot find symbol`** (XI-41): η εμβέλεια των `c1, c2` λήγει στο `}` του `do`, άρα δεν είναι ορατές **ούτε καν στη συνθήκη `while(...)`** ούτε μετά τον βρόχο!

**Διόρθωση (XI-42):** δηλώνουμε **`Color c1, c2;`** **πριν** το `do` και μέσα στον βρόχο κάνουμε μόνο ανάθεση (`c1 = new Color(…);`, `c2 = new Color(…);`).

## 6. Ομόκεντρα Τετράγωνα (`AlbersS`) — Πίνακας Αναφορών vs Garbage Collection (XI-44 … XI-48)

Ζητείται πρόγραμμα που σχεδιάζει `N` ομόκεντρα χρωματιστά τετράγωνα όπου κάθε χρώμα είναι συμβατό με το προηγούμενό του.

### Εκδοχή 1: Με πίνακα αναφορών `Color[]` (XI-46)

```java
int N = Integer.parseInt(args[0]);
Color[] cs = new Color[N]; // Πίνακας N αναφορών (αρχικά ΟΛΕΣ null!)

cs[0] = new Color((int)(Math.random()*256),
                  (int)(Math.random()*256),
                  (int)(Math.random()*256));

for (int i = 1; i < N; i++)
   do {
      cs[i] = new Color((int)(Math.random()*256),
                        (int)(Math.random()*256),
                        (int)(Math.random()*256));
   } while (!Luminance.compatible(cs[i-1], cs[i]));

// Σχεδίαση από το ΜΕΓΑΛΥΤΕΡΟ στο ΜΙΚΡΟΤΕΡΟ
double x0 = .5, y0 = .6, r = 0.3, rs = r / N;
for (int i = 0; i < N; i++) {
   StdDraw.setPenColor(cs[i]);
   StdDraw.filledSquare(x0, y0, r);
   r = r - rs;
}
```

> [!warning] Παγίδα 1 — Σειρά σχεδίασης (XI-47)
> Αν αλλάξουμε τον βρόχο σχεδίασης ώστε να ξεκινά από το μικρότερο (`r = 0.3/N; ... r += 0.3/N;`), κάθε νέο γεμάτο τετράγωνο **σκεπάζει** όλα τα προηγούμενα και τελικά φαίνεται **μόνο το τελευταίο (μεγαλύτερο) τετράγωνο**!

> [!warning] ➕ Παγίδα 2 — `new Color[N]` δεν φτιάχνει αντικείμενα `Color`!
> Η εντολή `Color[] cs = new Color[N];` δεσμεύει έναν πίνακα από `N` **κενές αναφορές (`null`)**. Αν καλέσεις `cs[0].getRed()` πριν εκτελέσεις `cs[0] = new Color(…);`, θα πάρεις **`NullPointerException`**.

### Εκδοχή 2: Χωρίς πίνακα — Garbage Collection σε δράση (XI-48)

Επειδή κάθε τετράγωνο χρειάζεται μόνο το προηγούμενο χρώμα για έλεγχο συμβατότητας, **δεν χρειάζεται πίνακας** — αρκούν δύο μεταβλητές `Color c1, c2;`:

```java
Color c1, c2;
c1 = new Color((int)(Math.random()*256),
               (int)(Math.random()*256),
               (int)(Math.random()*256));

double x0 = .5, y0 = .6, r = 0.3, rs = r / N;
for (int i = 0; i < N; i++) {
   do {
      c2 = new Color((int)(Math.random()*256),
                     (int)(Math.random()*256),
                     (int)(Math.random()*256));
   } while (!Luminance.compatible(c1, c2));
   StdDraw.setPenColor(c1);
   StdDraw.filledSquare(x0, y0, r);
   r = r - rs;
   c1 = c2; // το προηγούμενο αντικείμενο της c1 μένει χωρίς αναφορά → garbage collector!
}
```

- Μετά το **`c1 = c2;`**, το προηγούμενο `Color` στο οποίο έδειχνε η `c1` δεν έχει πλέον καμία αναφορά, άρα γίνεται υποψήφιο για συλλογή από τον **garbage collector** (XI-48).
- Επιπλέον, η μνήμη πέφτει από $O(N)$ (πίνακας `N` χρωμάτων) σε $O(1)$ (μόνο 2 ενεργά χρώματα κάθε στιγμή).

> [!note] ⚠️ Σημείωση (XI-48)
> Στην τελευταία επανάληψη (`i = N - 1`), ο βρόχος `do-while` παράγει ένα επιπλέον συμβατό χρώμα `c2` και το αναθέτει στο `c1`, το οποίο όμως δεν σχεδιάζεται ποτέ γιατί ο `for` τελειώνει. Οπτικά δεν επηρεάζει το αποτέλεσμα (σχεδιάζονται ακριβώς `N` τετράγωνα).

## 7. Αναπαράσταση Μνήμης (XI-51)

```
Διευθύνσεις μνήμης αντικειμένων:
  D0: [255]  D1: [0]  D2: [255]   ← αντικείμενο Color (magenta)
  D3: [0]    D4: [0]  D5: [0]     ← αντικείμενο Color (black)
  D6: [105]  D7: [105] D8: [105]  ← αντικείμενο Color (gray)

Μεταβλητές αναφοράς:
  magenta (στη θέση A0) περιέχει: D0   → δείκτης στο (255, 0, 255)
  gray    (στη θέση B0) περιέχει: D6   → δείκτης στο (105, 105, 105)
```

Επειδή η τιμή μιας μεταβλητής αντικειμένου είναι απλώς μια **διεύθυνση («δείκτης»)**, περνιέται και επιστρέφεται από μεθόδους (`lum(Color c)`, `Color toGray(Color c)`) εξίσου εύκολα και γρήγορα με έναν βασικό τύπο (XI-51).

## Συχνά Λάθη

- **Ξεχνάς `import java.awt.Color;`**: η `Color` δεν ανήκει στο `java.lang` (όπως η `String` ή η `Math`), οπότε θέλει ρητό `import`.
- **`c.brighter();` ή `c.darker();` χωρίς ανάθεση**: δεν τροποποιεί το `c` (η `Color` είναι αμετάβλητη).
- **Δήλωση μεταβλητής μέσα σε `do { ... }`** και χρήση της στη `while (...)`: σφάλμα μεταγλώττισης `cannot find symbol`.
- **Να ξεχάσεις το `(int)` στο `Math.round(lum(c))`**: η `Math.round(double)` επιστρέφει `long`, ενώ ο κατασκευαστής `Color(int, int, int)` απαιτεί `int`.
