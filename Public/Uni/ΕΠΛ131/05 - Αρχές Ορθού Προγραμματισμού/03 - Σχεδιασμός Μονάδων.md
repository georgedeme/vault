# 03 - Σχεδιασμός Μονάδων

Οι αρχές 9–14: πώς χωρίζουμε ένα πρόγραμμα σε μονάδες (μεθόδους, κλάσεις) ώστε να επεκτείνεται, να αλλάζει και να κατανοείται εύκολα (διαφάνειες V-23 … V-37).

## 9. Αρχή του Ανοικτού/Κλειστού – Open/Closed Principle (V-23, V-24)

> [!note] Ορισμός
> Οι κλάσεις, ενότητες, συναρτήσεις κτλ. να είναι **ανοικτές για επέκταση**, αλλά **κλειστές για τροποποιήσεις**.
> - Με άλλα λόγια, να κατασκευάζετε κλάσεις που οι άλλοι μπορούν να **επεκτείνουν**, αλλά **όχι να αλλάζουν**.
> - Έτσι **δεν επηρεάζονται** προγράμματα που ήδη αξιοποιούν κλάσεις στην υφιστάμενη μορφή τους· οι επεκτάσεις είναι κάτι **επιπρόσθετο**.

> [!important] Μηχανισμοί της Java για το «ανοικτό/κλειστό»
> - Προσθήκη νέων **πεδίων** (αντικειμένων) ή/και **μεθόδων** (π.χ. **overloading** – ίδιο όνομα, άλλες παράμετροι)
> - **Κληρονόμηση**, abstract base classes, **πολυμορφισμός** (θα έρθουν αργότερα στο μάθημα)

> [!note] Δομημένα, αρθρωτά προγράμματα (V-24)
> Διευκολύνουν:
> - τις **επεκτάσεις** τους, **χωρίς επηρεασμό** των υφιστάμενων τμημάτων, και
> - τις **αλλαγές** σε υφιστάμενα τμήματα, με **απόλυτα διαχειρίσιμο** τρόπο.
>
> Συνεπώς διευκολύνουν την **ενίσχυση της λειτουργικότητας** που παρέχουν.

> [!example]- Ανοικτό/Κλειστό στον κώδικα του μαθήματος
> Η `PrimeSieve` **επεκτάθηκε** με τη μέθοδο `displayPrimes` (IV-50) **χωρίς** να αλλάξει ο κώδικας του κόσκινου – απλά **προστέθηκε** μια μέθοδος και μία κλήση.
> Με overloading ➕: μπορείς να προσθέσεις `displayPrimes(boolean[] isPrime)` (με προεπιλογή 10 ανά γραμμή) δίπλα στην `displayPrimes(boolean[] isPrime, int n)`, χωρίς να «σπάσεις» κανέναν που ήδη καλεί την παλιά.

## 10. Αρχή της μίας ευθύνης – Single Responsibility Principle (V-25)

> [!note] Ορισμός
> **Κάθε κλάση ή συνάρτηση να εκτελεί μια μοναδική και σαφώς ορισμένη εργασία.** Έτσι μια κλάση έχει **μία και μόνο ευθύνη**:
> - ευθύνεται για την παροχή **μιας και μόνο λειτουργικότητας**, και
> - αυτό την καθιστά **πιο ανθεκτική**, αφού η ανάγκη για αλλαγή περιορίζεται σε **έναν μόνο λόγο**.
>
> Άμεση συνάφεια με την αρχή της **απλότητας**: απλοποιεί τη **διασύνδεση** της κλάσης και περιορίζει το περιεχόμενό της σε **μικρό αριθμό συναφών** στοιχείων.

> [!example]- Η τράπουλα (IV-26): μία μέθοδος, μία ευθύνη
>
> | Μέθοδος | Ευθύνη | Λόγος αλλαγής |
> |---|---|---|
> | `createDeck` | Δημιουργία | αλλάζει η σύνθεση της τράπουλας |
> | `shuffleDeck` | Επεξεργασία | αλλάζει ο αλγόριθμος ανακατέματος |
> | `displayDeck` | Παρουσίαση | αλλάζει η μορφή εξόδου |
> | `main` | Συντονισμός | αλλάζει η ροή του προγράμματος |
>
> Αντίθετα η αρχική `Deck` (IV-24) τα κάνει όλα μέσα στη `main` – τέσσερις λόγοι αλλαγής σε ένα μέρος.

## 11. Ελαχιστοποίησε τη σύζευξη – Minimize Coupling (V-26 … V-28)

> [!note] Ορισμός
> **Σύζευξη** (coupling): ο **βαθμός αλληλεξάρτησης** μεταξύ μονάδων λογισμικού – πόσο στενά συνδεδεμένες είναι δύο μονάδες (π.χ. δύο συναρτήσεις).
> - **Ισχυρή** σύζευξη (υψηλός βαθμός συνδεσιμότητας) **μειώνει την αυτοδυναμία** των εμπλεκόμενων μονάδων.
> - Ισχυρή σύζευξη υπάρχει όταν, για παράδειγμα, οι συναρτήσεις **μοιράζονται μεταξύ τους μεταβλητές**.
> - Ενδείκνυται η χρήση **αποκλειστικά τοπικών μεταβλητών**. Κατ' επέκταση η χρήση **καθολικών μεταβλητών** πρέπει να είναι **άκρως περιορισμένη** και **απόλυτα δικαιολογημένη**.

> [!warning] Μειονεκτήματα ισχυρής σύζευξης (V-27)
> - Αλλαγές σε μια μονάδα **αλυσιδωτά** ενδέχεται να απαιτούν αλλαγές σε άλλες.
> - Η **συναρμολόγηση** των μονάδων απαιτεί μεγαλύτερη προσπάθεια και χρόνο, λόγω των αλληλεξαρτήσεων.
> - Δυσκολεύεται η **δοκιμή** και η **επαναχρησιμοποίηση** μιας μονάδας, αφού πρέπει να ληφθούν υπόψη και οι εξαρτήσεις της – δεν υπάρχει **αυτοδυναμία** και **ανεξαρτησία**.

> [!important] Συνεπώς… (V-28)
> Ελαχιστοποίησε τη σύζευξη **μειώνοντας τις αλληλεξαρτήσεις** ανάμεσα στα τμήματα του κώδικά σου.
> - **Αδύνατη/χαλαρή σύζευξη** είναι χαρακτηριστικό ορθού σχεδιασμού και ορθά δομημένου κώδικα.
> - Σε συνδυασμό με **ισχυρή συνοχή**, ενισχύει την **αναγνωσιμότητα** και **συντηρησιμότητα**.

> [!example]- Ισχυρή vs χαλαρή σύζευξη σε Java ➕
> ```java
> // ✗ Ισχυρή σύζευξη: μοιραζόμενη (καθολική) μεταβλητή
> public class Gambler {
>     static int t;                          // καθολική
>     static void flip() { if (Math.random() < 0.5) t++; else t--; }
>     static boolean done(int goal) { return t <= 0 || t >= goal; }
>     // η flip και η done «ξέρουν» και οι δύο για το t – δεν δοκιμάζονται ανεξάρτητα
> }
>
> // ✓ Χαλαρή σύζευξη: ό,τι χρειάζεται περνά ως παράμετρος, το αποτέλεσμα επιστρέφεται (III-72)
> private static boolean Win(int s, int g) {
>     while (s > 0 && s < g) { if (Math.random() < 0.5) s++; else s--; }
>     return s == g;
> }
> ```
> Η `Win` εξαρτάται **μόνο** από τις παραμέτρους της – μπορείς να την καλέσεις/δοκιμάσεις από οπουδήποτε.

## 12. Μεγιστοποίησε τη συνοχή – Maximize Cohesion (V-29 … V-31)

> [!note] Ορισμός
> **Συνοχή** (cohesion): ο **βαθμός συνάφειας/σχετικότητας** των στοιχείων που απαρτίζουν μια μονάδα λογισμικού.
> - Με άλλα λόγια: **ανήκουν μαζί** οι μέθοδοι και τα δεδομένα που απαρτίζουν μια κλάση;
> - Η κλάση εξυπηρετεί κάποιο **κοινό σκοπό ή έννοια**;
>
> **Ισχυρή** συνοχή → ανθεκτικότητα, αξιοπιστία, επαναχρησιμοποίηση, κατανόηση. **Αδύνατη** συνοχή → δυσκολίες στη δοκιμή, συντήρηση, επαναχρησιμοποίηση, κατανόηση.

> [!note] Με απλά λόγια… (V-30)
> - Κώδικες με **συναφή λειτουργικότητα** πρέπει να ανήκουν μαζί στην **ίδια μονάδα** – π.χ. **βιβλιοθήκες** (όλα τα μαθηματικά στη `Math`).
> - Η **συστέγαση άσχετων** τμημάτων στην ίδια κλάση οδηγεί σε μια **δυσνόητη** κλάση χωρίς συγκεκριμένο σκοπό, που θα οδηγηθεί σε **αχρηστία**.

> [!warning] Θεωρητικά… (V-31)
> Μια μονάδα με **ένα και μόνο στοιχείο** έχει «τέλεια» συνοχή. **Στην πραγματικότητα δεν είναι έτσι**: πρέπει να υπάρχει **ορθό ισοζύγιο** ανάμεσα σε **συνοχή, πολυπλοκότητα ατομικών στοιχείων και σύζευξη**. Μοναδιαία στοιχεία είναι είτε **πολύ περίπλοκα**, είτε **πολύ περιορισμένα** και με **ισχυρές συζεύξεις** με άλλα (εξωγενή) στοιχεία.

> [!tip] Σύζευξη vs συνοχή – μην τα μπερδεύεις
>
> | | Σύζευξη (coupling) | Συνοχή (cohesion) |
> |---|---|---|
> | Μετράει | σχέσεις **ανάμεσα** σε μονάδες | σχέσεις **μέσα** σε μία μονάδα |
> | Θέλουμε | **χαμηλή** (χαλαρή) | **υψηλή** (ισχυρή) |
> | Σύνθημα | «low coupling, high cohesion» | |

## 13. Διαχωρισμός ευθυνών – Separation of Concerns (V-32 … V-35)

> [!note] Ορισμός
> **Διαφορετικές λειτουργικότητες** πρέπει να υλοποιούνται σε **ξεχωριστά** και με **ελάχιστες επικαλύψεις** τμήματα κώδικα – το καθένα με **τη δική του ευθύνη** (βλ. αρχή της μίας ευθύνης).
>
> Η εφαρμογή της:
> - οδηγεί σε **αρθρωτά** προγράμματα
> - **απλοποιεί** την ανάπτυξη και συντήρηση
> - διευκολύνει την **επαναχρησιμοποίηση** και την **ανεξάρτητη** ανάπτυξη/τροποποίηση τμημάτων

> [!important] Είναι μια έκφανση της γενικής στρατηγικής… (V-33)
> - Το πρόβλημα/στόχος **διασπάται σε απλούστερα τμήματα**, το καθένα με τον δικό του σαφή υπο-στόχο (ευθύνη) – **Διαίρει και βασίλευε**.
> - Η διάσπαση μπορεί να οργανωθεί σε διάφορα **στρώματα αφαιρετικότητας** – **σχεδιασμός σε στρώσεις** (layered design).

> [!note] Έχει άμεση συνάφεια με… (V-34, V-35)
> - Την **αρχή της απόκρυψης πληροφοριών** (λεπτομερειών υλοποίησης), αφού η **ενθυλάκωση** (encapsulation) είναι τρόπος επίτευξης άρθρωσης και διαχωρισμού ευθυνών.
> - Όπου ορίζονται **σαφείς διεπαφές** (interfaces), τμήματα του κώδικα μπορούν να τροποποιούνται και να βελτιώνονται **ξεχωριστά**, χωρίς να απαιτείται **γνώση των λεπτομερειών** ή **αλλαγή** σε άλλα τμήματα.
> - Η Java παρέχει πολλούς κατασκευαστικούς μηχανισμούς: **κλάσεις**, **συναρτήσεις/μέθοδοι**, **αντικείμενα** (ενθυλάκωση) – που δεν είναι άλλοι από τους τρόπους στήριξης της **κορυφαίας αρχής της αφαιρετικότητας**.

> [!example]- Δημιουργία / Επεξεργασία / Παρουσίαση
> Η `main` της IV-27 είναι το κλασικό σχήμα διαχωρισμού ευθυνών:
> ```java
> String[] deck = createDeck();   // Δημιουργία
> shuffleDeck(deck);              // Επεξεργασία
> displayDeck(deck);              // Παρουσίαση
> ```
> Αν αύριο η έξοδος πρέπει να πηγαίνει σε αρχείο αντί για οθόνη, αλλάζει **μόνο** η `displayDeck`.

## 14. Να αποκρύβεις τις λεπτομέρειες υλοποίησης – Hide Implementation Details (V-36, V-37)

> [!note] Ορισμός
> Αποκρύπτοντας τις λεπτομέρειες υλοποίησης, μπορείς να **αλλάζεις την υλοποίηση** μιας μονάδας επηρεάζοντας **στο ελάχιστο** τις μονάδες που τη χρησιμοποιούν.
> - Διαχωρισμός ανάμεσα στο **τι** (λειτουργικότητα παρέχεται) και το **πώς** (υλοποιείται).
> - **Ξεκάθαρες και σταθερές διεπαφές**, π.χ. βιβλιοθήκες.
> - Εάν ο ρόλος μιας μονάδας είναι **καθαρά βοηθητικός** προς άλλες, η ύπαρξή της **δεν χρειάζεται να είναι γνωστή** → **`private`**.
> - Αντικείμενα: μόνο μέθοδοι αναφοράς **`public`** – εσωτερική κατάσταση **`private`** → **ενθυλάκωση**.

> [!note] Και η απόκρυψη πληροφοριών (V-37)
> Είναι άμεσα σχετιζόμενη με την κορυφαία αρχή της **αφαιρετικότητας**.
> **Αφηρημένοι Τύποι Δεδομένων (ADT – Abstract Data Types) / Αντικείμενα:**
> - Η **δομή υλοποίησης αποκρύπτεται**.
> - Μόνο οι **μέθοδοι πρόσβασης** (access functions) δημοσιοποιούνται – για τη **δημιουργία** περιπτώσεων, την **ανάκληση** στοιχείων και την **αλλαγή** στοιχείων. Ουσιαστικά οι **διεπαφές** τους.

> [!example]- Απόκρυψη στον κώδικα του μαθήματος
> - `private static boolean allCollected(int[] cs)` και `private static int sum(int[] xs)` (IV-36): βοηθητικές → `private`.
> - `private static boolean Win(int s, int g)` (III-72).
> - `Math.sqrt(x)`: ξέρουμε **τι** κάνει, όχι **πώς** – και δεν μας νοιάζει. Αν η υλοποίηση αλλάξει σε νέα έκδοση της Java, ο κώδικάς μας δεν επηρεάζεται.
> - Η `shuffleDeck(String[] deck)`: ο καλών δεν ξέρει αν χρησιμοποιεί Fisher–Yates ή κάτι άλλο – μπορούμε να αλλάξουμε αλγόριθμο **χωρίς** να αγγίξουμε τη `main`.

## Πώς σχετίζονται (9–14)

```
Αφαιρετικότητα ──► Απόκρυψη λεπτομερειών (14) ──► ενθυλάκωση, private, ADT
      │                     │
      ▼                     ▼
Διαχωρισμός ευθυνών (13) ◄──► Μία ευθύνη (10)
      │
      ▼
Χαλαρή σύζευξη (11) + Ισχυρή συνοχή (12) ──► Ανοικτό/Κλειστό (9) ευκολότερο
```

## Συχνά Λάθη (στις απαντήσεις)

> [!warning] Συχνά Λάθη
> - Σύγχυση **σύζευξης** (ανάμεσα σε μονάδες – θέλουμε χαμηλή) με **συνοχή** (μέσα σε μονάδα – θέλουμε υψηλή).
> - Να λες ότι «τέλεια» συνοχή = ένα στοιχείο ανά μονάδα – η διαφάνεια V-31 λέει ρητά ότι **δεν** ισχύει στην πράξη.
> - Open/Closed: «κλειστή» **δεν** σημαίνει «δεν αλλάζει ποτέ» – σημαίνει ότι οι **χρήστες** της δεν χρειάζεται να αλλάξουν όταν **επεκτείνεται**.
> - Να ξεχνάς το παράδειγμα «καθολικές μεταβλητές → ισχυρή σύζευξη».
